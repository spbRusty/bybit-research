# GAP-анализ: рыночные тиковые признаки (ТЗ §12–§15)

Статус модуля `src/features_market.py` и ограничения данных на 2026-09-03.

## Реализовано и проверено

- `build_market_features(symbol)` агрегирует 5 тиковых потоков к минутным бакетам
  и возвращает `DataFrame[open_time (datetime ms), mk_*]` (41 колонка):
  - §12 стакан: `mk_best_bid/ask`, `mk_spread_pct`, `mk_imid`, `mk_imb1`,
    `mk_depth_bid5/ask5` + сырые `bid{i}_px/sz, ask{i}_px/sz` (i=1..5);
  - §13 order flow: `mk_buy_vol`, `mk_sell_vol`, `mk_flow_imb`, `mk_trade_count`,
    `mk_notional`, `mk_avg_size`, `mk_large_buy_vol`;
  - §14 futures: `mk_funding_rate`, `mk_oi`, `mk_oi_change`, `mk_mark_px`;
  - §15: `mk_buy_ratio`, `mk_liq_sell_vol`.
- 20 признаков зарегистрированы в REGISTRY (категория `market`).
- Sparse-стакан: берётся **последний non-NaN** каждой стороны уровня
  (`filter(is_not_nan()).last()` по `(bucket_ms, level)`), затем `pivot(on="level")`
  разворачивает уровни в колонки — без этого `.last()` захватывал NaN дельты
  и колонки уровней дублировали последнее значение всего бакета.
- Разреженность «состояний» (стакан, funding/OI, ratio) закрывается
  `forward_fill` по времени (только назад, **без look-ahead**), после чего
  считаются `mk_spread_pct/imid/imb1` (иначе разрежены ~1/13).
- Тесты: 4 новых в `tests/test_features.py` (bucket/no-lookahead, trades,
  orderbook sparse+уровни, futures/ratio last non-NaN) — весь набор 17/17 OK.
- Live-проверка: `build_market_features` на BTC/ETH/SOL — покрытие плотное
  (best_bid/ask/spread/imb ~100%, flow 15/16, oi_change 14/16).

## Критическое ограничение: свечи vs тики (нет пересечения)

| Источник | Покрытие BTCUSDT | Примечание |
|---|---|---|
| Свечи `bybit_rs/data/klines/linear` | до **2026-09-02 05:44** (74331 строк) | 1-min klines |
| Свечи `bybit_rs/data/klines_out/linear` | до 2026-08-31 08:38 (198804 строк) | фильтр: частичный |
| Тиковые потоки `collector/data/market` | **с 2026-09-02 21:38** | все 5 потоков |

**Между свечами и тиками — разрыв ~16 часов** (последняя свеча 05:44, первые
тики 21:38). Тиковые данные накапливаются только вперёд.

### Следствия

1. **Нет исторического стакана.** Orderbook.50 (`top-50`) имеет глубину данных
   только с момента запуска сервиса; бэкфилл стакана отсутствует. Исторические
   свечи (до 21:38) **нельзя** обогатить стакан/order-flow/funding — для них
   `mk_*` просто нет.
2. **Интеграция в основной пайплайн** (`features.add_features` на свечных
   данных): `build_market_features` возвращает бакеты, которые пересекаются со
   свечными `open_time` **только с 21:38 вперёд**. При outer-join по `open_time`
   историческая часть строк останется с `null` для `mk_*`, и модели придётся
   это учитывать (dropna или признаки доступности).
3. **Накопление** — по мере работы сервиса окно тиков растёт; полноценное
   обучение с рыночными признаками станет возможным, когда накопится
   достаточный пересекающийся интервал (часы/дни).

## Путь интеграции (предлагаемый)

1. В `main.py`/`features.py`: для строк, где есть пересечение, джойнить
   `build_market_features(symbol)` к свечному df по `open_time` (1m).
2. Свеча с `open_time=T` использует бакет `T` (тики `ts ∈ [T, T+60s)`) — данные,
   известные к закрытию свечи `T`, доступны на вход свечи `T+1`. **Без
   look-ahead.**
3. Для отсутствующих `mk_*` решить стратегию: `dropna` по затронутым строкам
   или индикатор доступности (не подставлять нули — это данные, а не отсутствие
   явления).
4. По мере накопления пересечения — расширить обучающий интервал.

## Отложено на потом (не блокирует)

- Бэкфилл тиков (стакан/order flow за исторический период) — требует отдельного
  загрузчика из REST-истории, которую Bybit предоставляет ограниченно.
- §15 basis (спот/фьючерсный спред): `basis_rate` из tickers для перпетуалов
  пуст — считать на Python по ценам спота+фьючерса (есть точка монтирования).
- **§21 внешние источники** — только интерфейс-scaffold, без источника данных
  (экономические календари, новости и т.п.). Не блокирует.

## §17 Рыночная широта (breadth) — РЕАЛИЗОВАНО 2026-09-04

Ранее §17 был отложен (нужен cross-sectional источник). Теперь широта считается
напрямую из уже собранных свечей всех символов юниверса — без новых данных:

- `src/features_breadth.py::compute_breadth(symbol_data)` ->
  `DataFrame[open_time, breadth]`, где
  `breadth = (advancing - declining) / present` по `is_green` символов в минуту;
  знаменатель — **фактически присутствующие** символы (null-строки исключаются),
  чтобы неполное покрытие не занижало широту.
- `features.add_features(..., breadth)` — join по `open_time` **перед** режимами,
  чтобы `market_breadth_regime` (§20) считался как производный.
- `main.py` — свечи юниверса грузятся один раз (`load_universe_data`), breadth
  считается один раз и передаётся во все `add_features`.
- Тесты: `test_market_breadth_regime` — весь набор **21/21 OK**.
