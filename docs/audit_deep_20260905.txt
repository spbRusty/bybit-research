Позиционный merge. Обе стороны используют идентичный Table::from([...])

================================================================================
2. ORDERBOOK: SNAPSHOT -> DELTA -> BOOK STATE
================================================================================

Это самый критический пункт.

Bybit WS protocol (orderbook.50.{symbol}):
  type: "snapshot" -> data.b = полный стакан (все уровни):
    [["50000","1.5"], ["49999","2.0"], ...]
  type: "delta" -> data.b = ИЗМЕНЕНИЯ:
    [["50000","0"]] (удаление), [["50100","0.5"]] (обновление)

Код parse_message (lines 208-232):
  let is_delta = v["type"].as_str() == Some("delta");
  for i in 0..OB_LEVELS {   // OB_LEVELS = 10
      let bp = bids.get(i).and_then(|x| x.as_array());
      let ap = asks.get(i).and_then(|x| x.as_array());
      if bp.is_none() && ap.is_none() { continue; }
      t[3].1.push(Cell::I(i as i64 + 1));  // level = i+1
      t[4].1.push(Cell::F(pf(bp...a.get(0))));  // bid_px
      t[5].1.push(Cell::F(pf(bp...a.get(1))));  // bid_sz

Ключевая проблема: Код итерирует i in 0..10 и читает bids[i] — позиционно.

  Snapshot: bids = [["50000","1.5"], ["49999","2.0"], ...]
    bids[0] = лучший bid, bids[1] = второй. Позиционный доступ КОРРЕКТЕН.

  Delta: bids = [["50000","0"]] (удаление уровня 50000)
    bids[0] = первый ИЗМЕНЁННЫЙ уровень.
    Код записывает level=1, bid_px=50000, bid_sz=0.
    Это НЕ level 1 — это изменение произвольного уровня.

Что происходит с is_delta: Флаг записывается в parquet, но НИГДЕ не
используется для реконструкции. Нет book state machine. Нет sequence gap
detection.

ob_capture_task (lines 549-564):
  Some((_key, rows)) => {
      for (i, (_, col)) in rows.into_iter().enumerate() {
          all_rows[i].1.extend(col);
      }
  }

Все строки (snapshot + delta) конкатенируются в all_rows. Parquet содержит
смесь snapshot-строк и delta-строк с одинаковой схемой.

Потребляет ли pipeline захваченные данные?

features_market.py читает из:
  MARKET_DATA_DIR / "orderbook" / "linear" / f"{sym}.parquet"
Захваты сохраняются в:
  CAPTURES_DIR / f"{event_id}.parquet"

Это РАЗНЫЕ пути. Данные захватов НЕ потребляются pipeline.

Цепочка доказательства:
1. Delta обрабатывается как snapshot (позиционный доступ) — level колонка
   содержит позицию в delta-массиве, а не реальный уровень книги
2. Book state не реконструируется (нет state machine)
3. is_delta флаг хранится, но не используется
4. Данные захватов не читаются features_market.py (другой путь)

> VERDICT: CONFIRMED BUG
> Delta-сообщения хранятся как snapshot. Реконструкция стакана невозможна.
> Однако данные захватов НЕ потребляются текущим pipeline -> impact на
> research = ZERO. Это BLOCKER для будущего использования orderbook captures,
> но не для текущих результатов.

5. PAPER TRADING
================================================================================

paper_run вызывается только из paper.py (grep: 1 совпадение).
Orchestrator НЕ вызывает paper_run.

Трейс execution lifecycle:

  entry = open(T+1)                     # из events
  stop_dist = stop_k_vol * vol * entry  # 2.0 * vol_gk_30d * entry
  stop = entry - side * stop_dist
  take = entry + side * 1.5 * stop_dist
  qty = floor(risk_usd / stop_dist / step) * step   # risk_usd = balance * 1%

Stop/take priority (_outcome):
  if side > 0:  # long
      if h_low <= stop: return "stop", stop    # СНАЧАЛА стоп
      if h_high >= take: return "take", take

Stop проверяется ПЕРВЫМ — консервативно.

Verified behavior (from runtime test):
  long, both hit (h_high>take, h_low<stop): reason=stop  OK (stop first)
  short, both hit: reason=stop  OK
  long, take only: reason=take  OK
  long, close: reason=close  OK

Position sizing:
  entry=100, stop=98, equity=10000: qty=50.0  OK (1% risk = $100, dist=2)
  entry=100, stop=99.999, equity=10000: qty=99999.999
  -- dist=0.001, qty взрывается. Нет max qty guard.

Fee: fee_round_trip = 0.0015 применяется ОДИН раз к fill_entry * qty —
это simplification (вместо отдельных fee на entry/exit), но корректно по
сумме.

Slippage: entry*(1+slip) для входа, exit*(1-slip) для выхода — корректно.

Множественные позиции: НЕТ. Trades обрабатываются последовательно.
Каждая сделка использует текущий state["balance"]. Нет concurrency.
open_positions в state не заполняется.

Look-ahead при определении результата: НЕТ. mfe/mae/return_{h}m — это
FUTURE metrics, вычисленные в events.py. Paper trading использует их для
SIMULATION (backtesting), не для принятия решения о входе. Вход决定 by
prefilter at time T, entry at open(T+1).

Research vs paper cost assumptions:
  Research: survival_cost = 0.002 (flat)
  Paper: fee=0.0015 + slippage=0.0002 = ~0.0017
  Research использует БОЛЬШУЮ стоимость -> консервативнее. Если гипотеза
  проходит research, она пройдёт и paper.

> VERDICT: PARTIALLY INTEGRATED
> Модуль реализован корректно (position sizing, fees, slippage, stop/take),
> но paper_run НЕ вызывается из orchestrator. Standalone модуль. Нет max
> qty guard (LOW).

6. FORWARD FILL / STALE MARKET DATA
================================================================================

Forward-filled колонки (features_market.py:177-180):
  state_cols = ["mk_best_bid", "mk_best_ask", "mk_funding_rate", "mk_oi",
                "mk_mark_px", "mk_buy_ratio", "mk_depth_bid5", "mk_depth_ask5"]
  out = out.with_columns([pl.col(c).forward_fill() for c in state_cols])

forward_fill() БЕЗ limit — Polars заполняет ВСЕ последующие null последним
известным значением бесконечно.

Частота обновления данных:
  mk_funding_rate, mk_oi, mk_mark_px: REST poll каждые 60с (FUTURES_POLL_SEC)
  mk_buy_ratio: REST poll каждые 300с (RATIO_POLL_SEC)
  mk_best_bid/ask, mk_depth_bid5/ask5: orderbook — не собирается permanent
    (event-driven only) -> всегда null

Что происходит при multi-hour gap:
  Колпетер падает на 2 часа
  При перезапуске: первый бакет с данными получает forward-filled значение
  ДО gap. Значение живёт пока не придёт новый tick.

Для funding_rate: funding меняется каждые 8ч -> 2ч gap = acceptable staleness
Для OI: меняется часто, но не драматично -> 2ч staleness = MEDIUM
Для mark_px: меняется непрерывно -> 2ч staleness = HIGH (may be significantly
  stale)

Look-ahead? НЕТ. Forward-fill использует ПРОШЛЫЕ данные. Feature на бакете
T использует данные <= T. Это НЕ leakage — это staleness (данные старше,
чем должны быть).

> VERDICT: MEDIUM ISSUE (data quality, not leakage)
> Forward-fill без limit -> значения могут жить бесконечно. Во время простоя
> колпетера features используют устаревшие данные. Не влияет на корректность
> period split, но снижает качество features.

7. CRASH RECOVERY ORDERBOOK CAPTURE
================================================================================

Lifecycle trigger-файла:
1. Python: trigger.write(_TRIGGERS_DIR) -> {event_id}.json
2. Rust trigger_watcher (2s scan) -> обнаруживает JSON -> отправляет в
   capture_manager
3. capture_manager -> ob_capture_task -> WS capture -> parquet ->
   fs::remove_file(trigger_path)

Crash during capture (step 3, до удаления):
  Trigger JSON остаётся в data/triggers/
  trigger_watcher starting with empty known map (in-memory only)
  Scan находит существующий JSON -> treated as NEW
  ob_capture_task запускается повторно
  Пишет в тот же {event_id}.parquet -> OVERWRITE предыдущего

Crash after deletion: trigger удалён -> нет дубликата.

Evidence:
  known map: HashMap<String, bool> в trigger_watcher — не персистится
  (line 443)
  known.retain(|k, _| Path::new(k).exists()) — на restart known пуст ->
  все файлы = new
  write_parquet пишет в {event_id}.parquet через atomic rename -> overwrite

Duplicate capture после restart = DATA OVERWRITE.
Первая capture теряется, заменяется второй.

> VERDICT: CONFIRMED BUG
> Orphaned triggers -> duplicate capture -> data overwrite. Impact: MEDIUM
> (в худшем случае capture перезаписывается другими market data). Не
> catastrophic для research, но нарушает data provenance.
