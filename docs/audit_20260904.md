# Полный аудит архитектуры — 2026-09-04

## Текущая архитектура

### Точка входа
`python -m src.main [--limit N] [--category linear|spot]`

### Pipeline flow (src/main.py)
```
1. liquidity_universe()       → data.py
2. load_btc() / load_eth()    → data.py
3. load_universe_data()       → data.py
4. compute_breadth()          → features_breadth.py
5. add_features()             → features.py (10 модулей)
6. rolling_gk()               → volatility.py
7. build_events()             → events.py
8. save_events()              → events.py
9. generate_hypotheses()      → hypothesis_generator.py
10. filter_by_freq()          → hypothesis_generator.py
11. run_research()            → research.py (discovery + val + OOS)
12. review()                  → critic.py (9 gates)
13. paper_run()               → paper.py (если critic PASS)
14. notify_research()         → notify.py
```

## Что уже автоматизировано (полностью)
1. Загрузка и валидация данных → data.py (duplicates, gaps, staleness, OHLCV)
2. Фильтр ликвидности → data.py (turnover, stability, freshness)
3. Вычисление признаков → features.py + 10 модулей (200+ признаков)
4. Вычисление волатильности → volatility.py (GK rolling)
5. Генерация событий → events.py (prefilter → future metrics)
6. Генерация гипотез → hypothesis_generator.py (rules-based)
7. Discovery + Validation + OOS → research.py (BH correction, split_periods)
8. Критические проверки → critic.py (9 gates)
9. Бумажная торговля → paper.py
10. Уведомления → notify.py

## Что требует ручного вмешательства
**NICHE** — main.py уже выполняет полный pipeline одной командой.
Но есть结构性 проблемы:

### Проблема 1: Нет данных StageResult
`run_research()` возвращает `dict`, а не структурированный результат.
Невозможно автоматически определить: STOP vs ERROR vs REJECT.

### Проблема 2: Нет data validation gate
data.py проверяет данные, но:
- Нет формального STOP при недостаточных данных
- Нет проверки временного покрытия
- Нет проверки минимального числа символов
- Просто логирует warnings, pipeline продолжает работу

### Проблема 3: Нет feature validation
Признаки вычисляются, но никогда не проверяются:
- Null rates
- Distribution stability
- Lookahead detection
- Feature metadata compliance

### Проблема 4: Parameter freeze неявный
Параметры выбираются в discovery, затем передаются как Hypothesis объект.
Это корректно, но формально:
- Нет frozen_marker
- Нет проверки что validation/oos не изменили параметры
- freeze неявный (просто тот же объект)

### Проблема 5: Нет registry lifecycle
Provenance существует, но нет:
- CANDIDATE → VALIDATED → ACTIVE → DEPRECATED
- Автоматических переходов по verdict
- Запрета на изменение ACTIVE стратегии

### Проблема 6: Hardcoded gates
- leakage: всегда True (документировано как architectural assumption)
- multiple_testing: всегда True (дублирует уже выполненную BH-поправку)

### Проблема 7: Нет error handling
pipeline возвращает 1 при отсутствии событий, но:
- Нет ERROR vs STOP различия
- Нет сохранения состояния при ошибке
- Нет retry capability

### Проблема 8: Provenance неполный
- Нет config hash
- data_version захардкожен "1.0"
- Нет commit hash
- Нет dataset_period

## Gate audit

| Gate | Проверяет | Данные | Формальный? |
|------|-----------|--------|-------------|
| leakage | Look-ahead | Архитектурное допущение | ⚠️ Doc-only |
| multiple_testing | BH коррекция | n_hypotheses, q_bh | ⚠️ Doc-only (BH уже выполнен) |
| sample_size | Достаточно событий | n_events_total >= 100 | ✅ |
| dependency | Независимость наблюдений | n_symbols >= 5 | ✅ |
| temporal_stability | Доля + месяцев | events + finalist condition | ✅ |
| costs | Discovery t-stat > порога | best_t > min_t_stat | ✅ |
| concentration | Концентрация по символам | top1_share <= 50% | ✅ |
| validation | EV > 0, n >= 100, t >= 2 | validation results | ✅ |
| oos | EV > 0, n >= 100, t >= 2 | oos results | ✅ |

## Gaps для автоматизации

1. **StageResult** — структурированный возврат каждого этапа
2. **Data validation gate** — STOP при недостаточных данных
3. **Feature validation** — null rates, distribution, quarantine
4. **Parameter freeze** — явный frozen marker + проверка
5. **Registry lifecycle** — CANDIDATE→VALIDATED→ACTIVE
6. **Error handling** — ERROR vs STOP vs REJECT
7. **Provenance** — config hash, data version, commit
8. **Acceptance report** — формальный acceptance criteria
